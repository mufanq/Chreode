# 科研项目开发、评审与证据记录规范

版本：`2026-09-06.1`。生效日期：2026-09-06。依据：用户本次关于科研项目开发、合并和实验质量的明确要求。

本规范适用于科研代码、研究方法、训练与评估配置、实验脚本、实验结果及分析文档。
Pull Request（PR，拉取请求）是相关修改进入主分支的唯一入口。已有项目规范继续适用；
本规范补充科研工作的证据和评审要求，不改变既有保密、发布权限及资源使用边界。

## 1. 子模块与 worktree 开发

1. 科研项目代码以独立 Git 仓库维护，由主仓库通过 submodule（子模块）固定版本；
   后续开发使用该子仓的独立 worktree（关联工作目录）和任务分支。
   主仓库的科研规范、工作簿及子模块指针修改，也使用 worktree、任务分支和 PR。
2. 开工记录 remote、基准分支与 commit、任务分支、worktree 及已有未提交修改。
   默认新任务分支使用 `codex/<topic>`，已有明确项目约定优先。
   不直接在主分支、共享工作目录或子模块的游离 HEAD 上开发，不覆盖他人修改。
3. 子仓先提交并推送任务分支、创建 PR；主仓库通过自己的 PR 更新子模块指针，
   链接子仓 PR 与准确 commit。主仓库合并指针更新前，确认子仓目标 commit
   已按其 PR 流程合并、能够从授权远端获取。
4. 第三方参考库保持子模块形式；需要修改时，确认授权的可写仓库与 PR 目标，
   不把无法交付的本地第三方 checkout 当作已完成实现。
5. 尚未满足独立仓库和 worktree 要求的科研代码，先记录并完成后续开发所需的迁移。
   迁移不能覆盖现有改动、擅自改写历史、创建公开远端或绕过项目的保密限制。
   历史资料归档不因本规范而自动恢复开发、公开发布或重新运行实验。

## 2. PR、独立子 agent 评审与合并

1. 实现 agent 完成必要的代码、文档和验证，将证据随改动提交并推送。
2. 每个 PR 至少由一个未参与该实现的子 agent 独立评审。评审记录必须绑定明确的
   `base commit → head commit`，实际检查 diff、相关实现上下文与证据。
   实现 agent 自评不能替代独立评审。
3. 将全部反馈及时写入 PR 记录，保留原始内容和来源；逐项记录修复、验证与复评结果。
   所有问题修复并经评审员确认后，才可以进一步合并。
   如果原判断确实错误或不适用，由评审员依据证据撤回并说明原因，不删除原意见。
4. “待处理”“延期”“接受风险”不等于问题已解决，不能据此宣布评审通过。
   适用证据缺失或问题未解决时，保持草稿或禁止合并。
5. 评审后代码、配置、依赖、实验解释或结论变化，评审员必须检查新增 diff，
   并重新运行受变化影响的验证。无需机械重复不受新增修改影响的昂贵实验。
6. 合并前核对评审覆盖最终待合并版本、必答项完整、适用验证通过、全部反馈关闭，
   并满足远端已有的检查及合并规则。主分支发生影响验证的变化时，重新确认相关证据。
7. 子 agent 评审是可追溯的技术评审，不得伪装成另一名真人的 GitHub approval，
   也不能替代仓库要求的真人批准。不得为通过本流程擅自修改分支保护或权限策略。

### 最终版本确认不产生无限记录递归

先对确定的实现 commit 评审，再提交已经产生的评审原文、整改和验证记录。
如果最后新增 commit 只忠实归档已有评审结论，评审员检查该增量后，
在 PR 评论或评审元数据中明确确认最终 head commit。
这一次最终版本确认不要求再产生一个“记录确认”的 commit。
全部实质性问题和处理过程仍必须入库；若记录增量改变规范含义、代码、分析或结论，
必须正常复评，不能套用纯归档处理。

## 3. 每个 agent 都要记录自己的贡献

每个参与实现、实验、分析或评审的 agent，均在同一份 PR 记录中补充自己的工作条目。
记录模板见 [record-template.md](record-template.md)；PR 正文入口见
[research.md](../../.github/PULL_REQUEST_TEMPLATE/research.md)。
项目可以沿用已有等价记录文件，但不能丢失以下字段。

| 字段 | 要求 |
|---|---|
| 时间和身份 | 开始及结束时间、时区、agent 名称、会话或任务标识 |
| 实际模型 | 可核验的模型信息；只能确认配置名称时分别注明，实际模型不可用写“未证实” |
| 任务和版本 | 本次负责的任务、仓库、分支、worktree、输入 HEAD 与输出 HEAD |
| 输入 | 任务要求、用户原文或资料来源、所读代码和配置的版本 |
| 输出 | 修改文件、实验产物、分析、评审意见及可定位的链接或路径 |
| 测试和限制 | 运行命令、配置、检查结果、未覆盖范围、失败和未证实项 |
| 交接 | 对应 PR、反馈来源、修复 commit、复评对象和结论 |

实际模型元数据无法核验时如实注明，不自动构成纯文档改动的验收失败；
这不豁免任何适用的工程、科研或实验验收证据。若任务要求特定实际模型，仍须核验后才能宣称满足。

记录可核验的动作和结论，不要求记录 agent 的内部思考过程。
agent、模型和会话信息是追溯元数据，不作为 commit 的 AI 作者或共同作者署名。

## 4. PR 分类与必答问题

类型可多选；所有适用类型都要回答，不能只选最容易证明的一类。

| 类型 | 必答问题 | 证据 |
|---|---|---|
| 工程 | 实现或修复什么？是否符合良好工程规范、项目既有结构及用户工程偏好？是否复用现有模块？配置语义、错误处理、兼容性和测试是否合理？ | 适用规范链接、设计理由、接口和配置变化、相关检查与测试结果 |
| 科研 | 回答什么科研问题？谁在何时提出？和用户讨论的原文是什么？有什么参考引用？实现如何检验假设？ | 任务相关原文及来源位置、引用、假设和对照、实际目标与实现版本 |
| 实验结果 | 为什么运行实验、引入实验脚本、保存脚本备份或分析结果？是否公平比较？是否有意义？支持什么结论？ | 运行协议、完整命令与配置、代码及数据版本、对照表、原始结果、统计口径和限制 |

每个必答项必须区分三种状态：**已验证**、**不适用**、**未证实**。
“不适用”要给出依据，例如准确的纯文档 diff、未改变运行入口和实验解释的文件范围。
适用但没跑、缺日志、缺原文或缺对照，一律写“未证实”，不能伪装成“不适用”。
纯文档修订不要求为了填表运行无关训练；实验脚本、配置和结果分析即使没有模型源码改动，
也不能因此自动免除相应实验或科研问题。

用户原文只归档任务相关内容，保留时间、会话或来源位置；解释与结论分开，
不把 agent 摘要冒充用户原话。保密限制继续有效：受限原文保留在授权位置，
对外 PR 仅使用允许披露的引用与定位，不得为了填模板公开私密讨论或受限材料。

## 5. 实验公平性、意义与结论

1. 比较前记录研究问题、实际训练和评估目标、数据版本及划分、预处理、训练和评估协议、
   初始化或 checkpoint 来源、预算、随机种子或重复次数、指标定义、模型选择方式、
   硬件和软件环境。
2. 实际目标须由 resolved config、激活的实现组件、代码版本、checkpoint 目标与来源、
   运行 manifest 相互核验。项目名称、分支和 run 名称不能证明实际执行目标。
3. 对照优先只改变待检验因素。无法相同时，逐项披露差异与解释限制，
   不把不可比数字直接归因于新方法。开关是否生效要验证实际行为或产物。
4. 在看结果之前确定主要指标、统计方法、可接受数值容差、效果判断标准及其依据，
   保存确定时间和记录版本。不得看到失败或负结果后追改阈值让实验“通过”。
   科学上需要修订协议时，记录理由和新版本，重新生成相应可比证据。
5. 采用适合任务的实验规模和重复次数，不机械复制其他项目的固定噪声阈值，
   不擅自把内部验证扩大为昂贵的正式实验。少量重复只能支持相应范围的初步判断。
6. 区分代码已实现、实验已运行、产物已核验和结论得到支持。
   如实记录改善、劣化、无明确差异或证据不足，以及结果的意义和适用边界。

## 6. 既有实验复现、数值回归与新特性

功能修改、训练或评估路径变化、依赖及数据处理变化，以及较大的破坏性变更，必须回答：

> 修改后，原本能运行的哪些实验仍能运行？数值结果是否仍符合原协议及预先约定的容差？

先列受影响实验族及影响依据，再选择能覆盖影响的代表实验。
验证范围与声明范围一致，不用一个冒烟结果宣称全部实验均不受影响。
新特性必须建立下面三组对照：

| 对照 | 目的 | 证据 |
|---|---|---|
| 修改前代码的基线 | 确认原实验及参考数值 | commit、协议版本、完整配置、命令、环境、产物、指标 |
| 修改后代码，关闭新特性 | 证明旧路径和基础架构性能仍可复现 | 相同条件、实际关闭行为、数值差异、预先确定的容差及结论 |
| 修改后代码，打开新特性 | 判断新特性的效果 | 相对关闭时的差异、效果大小、稳定性、成本及改善或劣化结论 |

现有基线只能在**协议完全一致、代码与配置版本可核验、原始产物可追溯**时复用。
必须逐项核对前述数据、划分、预处理、目标、初始化、预算、随机性、指标、模型选择和环境，
并记录复用的依据；不能只因 run 名或一张历史结果表相似就复用。
无法满足时，在当前同一协议下重跑匹配基线。

没有可开关新特性的功能修改，仍需比较修改前后的受影响实验，并说明开关对照不适用。
不能把“没有开关”当作旧实验或数值回归的豁免。
数值验证使用与目标等价的环境，明确本任务要求逐位一致、逐元素容差、短程训练回归，
还是完整指标复现。单测、形状、加载成功或 loss 有限不能替代受影响的数值验证。
硬件变化时在同一新硬件协议内建立基线并比较，不能声称跨硬件逐位一致。

修复已证实的数值错误时，不要求复现错误数值；记录旧结果为何无效、修复后的正确依据、
应撤回的历史结论，并验证不受该错误影响的行为。
新特性的负结果可以如实提交，不把“必须优于基线”当作填报条件。
关闭新特性后的兼容性或数值回归失败，不能用新功能更强来抵消。

## 7. 反馈保存、及时 commit 与同步

1. 在形成可评审改动、收到反馈、完成整改和取得验证结果后，及时更新记录，
   随对应 commit 推送至已授权远端的任务分支，不攒到合并后补写。
2. 反馈及处理过程采用只追加记录：保留原始评审意见、评审 commit、PR 评论链接、
   修复 commit、验证和复评结论。更正时追加更正及原因，不覆盖或删除历史反馈。
   当前状态表可以更新，但每次状态变化须链接到新增的处理记录。
3. GitHub PR 通过向同一任务分支正常 push 更新，并核对远端 PR 的 head commit；
   其他评审系统使用各自专用更新命令。禁止强推共享分支。
4. push 前核对文件范围、凭证泄露和项目保密要求；不提交 secret、无关改动或大体积原始产物。
   大产物保存在既有授权存储，Git 记录可复现的索引、校验值和必要摘要。
5. 本规范不覆盖项目已有的 local-only、禁止推送或 private-only 限制。
   无授权远端或明确仅本地的项目，本地提交规范和记录、注明远端同步不适用及依据；
   后续功能开发在授权仓库和 PR 路径明确前不能绕过合并要求。
   private-only 项目只能推到核验过的授权私有远端。
6. 凭证或权限阻塞时保留本地 commit，明确报告尚未同步的仓库、版本和原因；
   不创建公开仓库、不切换未授权 namespace、不更改权限策略作为替代。
7. 每项事实在项目内保留一个权威记录位置，PR、README 和主仓库通过链接引用，
   避免复制多份持续漂移的结论。

## 8. 公开仓库的记录边界

本仓库公开可读。只提交可公开的通用规范和与本仓库相关、已允许披露的工程及科研证据。
不得把私人对话、内部路径、受限项目或仓库名称、账号与主机标识、凭证或未获准公开的结果
复制到 PR、commit、评审反馈或本仓文档中。评审记录同样受此边界约束。

科研问题的来源优先使用公开 issue、讨论、论文或其他公开可定位记录。用户讨论涉及受限
内容时，完整原文保留在授权的私有记录，公开 PR 仅保存获准披露的准确引文或非敏感引用，
并标明公开证据的范围；不可假造来源、把摘要冒充原话，也不公开私有存储路径。
若独立评审员无法获准访问必要证据，应标记“未证实”并保持不可合并，不能用隐私限制
掩盖证据缺口。与私有集成仓的关联只公开可披露的版本和引用。
